# infra/ansible/ — turn bare VMs into a k3s cluster

Reuse your provisioning role and add k3s. Roles, not one giant playbook.

**Roles:**
- `hardening` — non-root user, SSH-keys-only, firewall, (optional) fail2ban. You have this already.
- `k3s-server` — install k3s on the control-plane; capture `/var/lib/rancher/k3s/server/node-token`.
- `k3s-agent` — join each worker with that token + the server's private IP.

**Inventory:** generate (or hand-write) from Terraform outputs — one `server` host, N `agents`.

**Requirements:**
- Idempotent: a second `ansible-playbook` run reports `changed=0`.
- Fetch `/etc/rancher/k3s/k3s.yaml` back to your machine, rewrite `server:` to the public IP,
  save as a gitignored kubeconfig.

**Acceptance:**
```bash
kubectl get nodes -o wide      # control-plane + all workers = Ready
```
Disable k3s's bundled Traefik (`--disable traefik`) only if you install ingress-nginx instead —
either is fine, just be consistent and document it in ARCHITECTURE.md.

# infra/ansible/ — turn bare VMs into a k3s cluster

## Layout

```
infra/ansible/
├── ansible.cfg
├── requirements.yml         # Galaxy collections (community.general, for ufw)
├── site.yml                 # hardening -> k3s-server -> k3s-agent, in order
├── fetch-kubeconfig.yml     # run after site.yml: pulls + rewrites kubeconfig
├── group_vars/
│   └── all.yml               # vpc_cidr, k3s_version - shared across all hosts
├── inventory/
│   └── hosts.ini             # AUTO-GENERATED by infra/terraform - do not hand-edit
└── roles/
    ├── hardening/             # non-root, SSH-keys-only, UFW firewall, fail2ban
    ├── k3s-server/            # installs k3s server, captures the join token
    └── k3s-agent/             # joins each worker using that token
```

## Prerequisites

```bash
pip install ansible --break-system-packages   # if not already installed
cd infra/ansible
ansible-galaxy collection install -r requirements.yml
```

Confirm the inventory Terraform generated is actually there and populated:
```bash
cat inventory/hosts.ini
```
You should see a `[server]` host and 2+ `[agents]` hosts with real IPs, not
placeholders. If this file is missing or empty, go back and run `terraform
apply` in `infra/terraform/` first - this role assumes it already exists.

## Usage

**1. Test connectivity first** (catches SSH/key problems before anything else runs):
```bash
ansible all -m ping
```
Expect `SUCCESS` for `server`, `agent-1`, `agent-2`.

**2. Run the full playbook:**
```bash
ansible-playbook site.yml
```
This runs three plays in order: harden every node, install the k3s server,
then join the agents. Read the recap at the bottom - `failed=0` for all hosts.

**3. Confirm idempotency** (the brief's explicit requirement):
```bash
ansible-playbook site.yml
```
Run it again, immediately. The final recap should show `changed=0` across
the board - a second run should do nothing but confirm the state.

**4. Fetch your kubeconfig:**
```bash
ansible-playbook fetch-kubeconfig.yml
```
This saves a ready-to-use kubeconfig at the **repo root** as `phoenix-config`
(gitignored). Use it with:
```bash
export KUBECONFIG=$(pwd)/../../phoenix-config   # from infra/ansible/
# or, from the repo root:
export KUBECONFIG=$(pwd)/phoenix-config
```

**5. Acceptance check:**
```bash
kubectl get nodes -o wide
```
You should see the server plus both agents, all `Ready`.

## Design notes

- **Token handoff is file-based, not just an in-memory fact.** The
  `k3s-server` role fetches `/var/lib/rancher/k3s/server/node-token` down to
  `infra/ansible/.cache/node-token` on your machine (gitignored). The
  `k3s-agent` role reads it from there. This means you can add a 4th agent
  later and run `ansible-playbook site.yml --limit agent-4` without needing
  to re-run the server play in the same execution.
- **Traefik decision:** we keep k3s's bundled Traefik rather than passing
  `--disable traefik` - one less moving part for a 3-node capstone. This is
  set via `k3s_server_extra_args` in `roles/k3s-server/defaults/main.yml`.
  Mirror this same choice in `docs/ARCHITECTURE.md` per the brief's
  instruction to "be consistent and document it."
- **SSH hardening uses a drop-in file**, not edits to the base
  `sshd_config`, because Ubuntu's cloud-init already ships its own
  `50-cloud-init.conf` and `sshd` uses first-match-wins - our
  `00-hardening.conf` is deliberately numbered to be read first.
- **UFW rules mirror the Terraform security groups** exactly (see the
  comments in `roles/hardening/tasks/main.yml`), so the host firewall and
  the AWS firewall agree - defense in depth, not just one layer.
- **`host_key_checking = False`** in `ansible.cfg` is a deliberate
  convenience for this lab context - every time you replace an EC2 instance
  (same Elastic IP, new host key), you'd otherwise have to manually
  `ssh-keygen -R <ip>` before Ansible would connect. Not something you'd want
  on a shared production inventory.
